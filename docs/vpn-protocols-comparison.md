# Сравнительный анализ VPN-протоколов

> Документ подготовлен с позиции практикующего специалиста по информационной безопасности:
> акцент на криптостойкость, площадь атаки, эксплуатационные риски и применимость,
> а не на маркетинговые заявления вендоров.
>
> Ревизия: 2026-09. Оценки производительности — ориентировочные (порядок величины),
> зависят от железа, MTU, offload-движков и версий стека.

## 0. Краткий вердикт (TL;DR)

| Задача | Рекомендация 2026 | Категорически не рекомендуется |
|---|---|---|
| Site-to-site между площадками | IKEv2/IPsec (ESP, AES-GCM/ChaCha20) или WireGuard | PPTP, IKEv1 Aggressive Mode с PSK |
| Remote access для сотрудников | IKEv2/IPsec + MOBIKE или WireGuard (+ поверх — MFA/IdP) | PPTP, L2TP без IPsec, SSTP |
| Обход NAT/фаервола, «только 443» | OpenVPN/TCP, OpenConnect (DTLS+TLS), SoftEther | Голый GRE, голый ESP |
| Максимальная производительность | WireGuard (kernel), IPsec с AES-NI/offload, OpenVPN DCO | OpenVPN/TCP (TCP-over-TCP meltdown) |
| Мобильные клиенты, роуминг Wi-Fi↔LTE | IKEv2+MOBIKE, WireGuard | OpenVPN без `--float`, SSTP |
| Mesh между множеством узлов | WireGuard (Tailscale/Netbird/Nebula) | Полносвязный IPsec вручную |
| Среда с активным DPI | VLESS+REALITY, Hysteria2, AmneziaWG, obfs4 | Ванильные WireGuard/OpenVPN/IPsec |
| Требование сертификации (ГОСТ/FIPS) | IPsec с сертифицированным СКЗИ | Всё, что не в реестре |

**Главный тезис:** за последние 10 лет отрасль сошлась на трёх живых семействах —
**IPsec/IKEv2**, **TLS-VPN (OpenVPN/OpenConnect)** и **WireGuard**. Всё остальное — либо
их производные, либо легаси, либо узкоспециализированный инструмент обхода цензуры.

## 1. Методология оценки

Каждый протокол оценивается по девяти осям:

1. **Криптостойкость** — примитивы, PFS, длина ключей, наличие AEAD.
2. **Аутентификация** — что именно проверяется и насколько это надёжно.
3. **Площадь атаки** — объём кода в привилегированном контексте, парсеры, история CVE.
4. **Производительность** — накладные расходы, место исполнения (kernel/userspace).
5. **NAT/FW traversal** — выживаемость в реальных сетях.
6. **Мобильность** — переживание смены IP/интерфейса.
7. **DPI-устойчивость** — детектируемость по сигнатурам.
8. **Экосистема** — нативная поддержка в ОС, зрелость реализаций.
9. **Пост-квантовая готовность** — наличие гибридных/PSK-режимов.

Шкала: 🟢 хорошо · 🟡 условно · 🔴 плохо/небезопасно · ⚫ мертво

## 3. Детализация по семействам

### 3.1 IPsec-семейство

| Параметр | IKEv1 | IKEv2 |
|---|---|---|
| RFC | 2409 (устарел), 8247 | 7296, 8247, 9370 |
| Количество сообщений (handshake) | 6 (Main) / 3 (Aggressive) | 4 (IKE_SA_INIT + IKE_AUTH) |
| EAP (сертификаты + логин) | только XAUTH (костыль) | нативно (EAP-TLS, EAP-MSCHAPv2) |
| Роуминг между сетями | нет | MOBIKE (RFC 4555) |
| NAT traversal | NAT-T надстройка | встроен |
| Dead Peer Detection | RFC 3706, опционально | встроенный liveness check |
| Асимметричная аутентификация | нет | да (сервер — сертификат, клиент — EAP) |
| Фрагментация IKE | ломается на больших сертификатах | RFC 7383 |
| Пост-квантовые режимы | нет | RFC 8784 (PPK), RFC 9370 (Multiple Key Exchanges → ML-KEM) |
| Вердикт | 🔴 вывести из эксплуатации | 🟢 целевой стандарт |

**Ключевой риск IKEv1:** Aggressive Mode с PSK отдаёт хеш PSK до аутентификации —
офлайн-перебор (`ikeforce`, `psk-crack`) на GPU занимает часы для типичного «корпоративного»
пароля. Если у вас это включено — это не «легаси», это открытая дверь.

**Типовой безопасный набор для IKEv2 (2026):**
```
IKE:  AES-GCM-256 / PRF-HMAC-SHA384 / ECP-384 (или X25519) + ML-KEM-768 (RFC 9370)
ESP:  AES-GCM-256 или ChaCha20-Poly1305
Auth: X.509 (ECDSA P-384) с обеих сторон + EAP-TLS для пользователей
Rekey: IKE SA — 4 ч, Child SA — 1 ч, PFS обязателен
```
Запрещать: DH group 1/2/5 (768/1024/1536-bit MODP), 3DES, HMAC-MD5, любой не-AEAD режим
без явного обоснования, `modeconfig` без проверки сертификата.

### 3.2 TLS-VPN

| Параметр | OpenVPN | OpenConnect/AnyConnect | SSTP | SoftEther |
|---|---|---|---|---|
| Управляющий канал | TLS | HTTPS (CONNECT) | HTTPS | HTTPS |
| Канал данных | собственный, UDP/TCP | DTLS (ESP-подобный) | тот же TCP | TCP/UDP/ICMP/DNS |
| Защита управляющего канала | `tls-crypt-v2` (скрывает даже handshake) | TLS | TLS | TLS |
| Работа через HTTP-прокси | да | да | да | да |
| Открытый код | да (GPL) | клиент+ocserv — да | нет | да (Apache 2.0) |
| MFA | через плагины/`auth-user-pass-verify` | нативно (AAA) | через NPS | RADIUS |
| Главный минус | userspace-производительность | привязка к вендорскому UX | Windows-центричность | 🔴 большая площадь атаки |

**О `tls-crypt-v2`:** это не «ещё одно шифрование», а защита от активного сканирования.
Без него OpenVPN-сервер отвечает на неаутентифицированный TLS ClientHello и однозначно
детектируется сканером. С ним — молчит. Включать всегда.

**TCP-over-TCP:** OpenVPN/TCP и SSTP инкапсулируют TCP в TCP. При потерях два независимых
механизма ретрансмиссии начинают бороться друг с другом («meltdown») — пропускная способность
проваливается нелинейно. Использовать только как запасной путь, не как основной.

### 3.3 WireGuard

| Свойство | Оценка | Комментарий |
|---|---|---|
| Объём кода | ~4 000 строк | против ~100 000 у OpenVPN и ~400 000+ у strongSwan/IPsec — на порядки меньшая площадь аудита |
| Криптографическая гибкость | **отсутствует** | это фича: Noise_IKpsk2, ChaCha20-Poly1305, Curve25519, BLAKE2s, HKDF. Нет согласования → нет downgrade-атак |
| Обновление криптографии | только смена версии протокола | обратная сторона той же медали |
| Аутентификация | статические публичные ключи | 🔴 нет PKI, нет отзыва, нет срока действия. В масштабе — только через оркестратор (Tailscale/Netbird/Firezone) |
| Состояние | «stateless-подобный» | сервер отвечает только на валидные пакеты → невидим для сканеров портов |
| Защита от DoS | cookie-механизм (как в DTLS/IKEv2) | под нагрузкой выдаёт cookie вместо вычисления DH |
| Утечка приватности | 🟡 | последний известный endpoint клиента хранится в памяти сервера; на клиенте IP сервера — в конфиге |
| Логирование | ❗ по умолчанию `AllowedIPs` статичен | для журналирования подключений нужны внешние средства |
| DPI | 🔴 | первый байт = тип сообщения (1–4), фиксированные длины 148/92/32+ байт → тривиальная сигнатура |
| Пост-квант | 🟡 через `PresharedKey` | 256-битный PSK даёт PQ-защиту канала; Rosenpass автоматизирует его ротацию через ML-KEM/McEliece |

**Практическое замечание:** «WireGuard не логирует» — это не преимущество, а требование
компенсирующего контроля. Для корпоративного применения нужен слой управления
(Firezone, Netbird, Headscale, Defguard), иначе вы получите неуправляемый набор ключей
без отзыва.

### 3.4 Протоколы обхода блокировок

Отдельный класс: их цель — **неотличимость**, а не только конфиденциальность.
Криптография здесь часто вторична (многие не дают PFS).

| Протокол | Модель маскировки | Активное зондирование | Слабое место |
|---|---|---|---|
| Shadowsocks (AEAD) | поток без сигнатуры | 🟡 уязвим к replay без `SIP004`/2022-режима | нет PFS, компрометация пароля = расшифровка архива |
| VMess | своя обёртка | 🔴 детектируется | устарел, не использовать |
| VLESS+XTLS Vision | настоящий TLS 1.3 | 🟢 | требует валидного домена и сертификата |
| REALITY | **заимствует TLS-сертификат чужого сайта** | 🟢 лучшее сопротивление | зависит от доступности «прикрытия»; юридически спорно |
| Trojan | неотличим от HTTPS, при неверном пароле отдаёт реальный сайт | 🟢 | fallback-сайт должен быть правдоподобен |
| Hysteria 2 | QUIC + агрессивный congestion control | 🟡 UDP/QUIC могут просто резать | «нечестный» к соседям по каналу CC |
| NaiveProxy | использует сетевой стек Chrome целиком | 🟢 идеальный JA3/JA4-отпечаток | производительность ниже |
| AmneziaWG | добавляет мусорные пакеты и случайные заголовки к WG | 🟢 | несовместим с ванильным WG |
| obfs4 | рандомизированный поток + мостовой секрет | 🟢 к пассивному, 🟢 к активному | низкая скорость (Tor) |

## 4. Криптографические примитивы

| Протокол | Обмен ключами | Симметричный шифр | Целостность | Хеш/KDF | Downgrade возможен? |
|---|---|---|---|---|---|
| PPTP | — (из пароля) | RC4 40/128 | **нет** | MD4 | н/п (всё сломано) |
| L2TP/IPsec | DH 2048+ / ECDH | AES-CBC/GCM | HMAC-SHA2 | SHA-2 | 🟡 да, при слабой политике |
| IKEv2 | DH/ECDH/X25519 (+ML-KEM) | AES-GCM, ChaCha20 | встроено (AEAD) | SHA-2, PRF | 🟡 согласование → нужна жёсткая политика |
| OpenVPN | TLS 1.3 (X25519/ECDHE) | AES-256-GCM, ChaCha20 | AEAD | SHA-2 | 🟢 нет при `tls-version-min 1.3` |
| WireGuard | Noise_IKpsk2, X25519 | ChaCha20-Poly1305 | Poly1305 | BLAKE2s + HKDF | 🟢 **невозможен by design** |
| MACsec | MKA (802.1X) | AES-GCM-128/256 | GCM | — | 🟢 |
| MASQUE | TLS 1.3 в QUIC | AES-GCM / ChaCha20 | AEAD | SHA-2 | 🟢 |
| Shadowsocks | **нет** (PSK из пароля) | ChaCha20-Poly1305 | AEAD | HKDF-SHA1 | 🔴 нет PFS |
| ГОСТ-VPN | VKO ГОСТ Р 34.10-2012 | Кузнечик / Магма | ИМИТА / HMAC-Стрибог | Стрибог | зависит от реализации |

**Принцип:** любой протокол без AEAD (encrypt-then-MAC в лучшем случае, MAC-then-encrypt —
в худшем) сегодня считается технически долгом. Любой протокол без PFS означает: перехваченный
сегодня трафик расшифруют завтра, получив ключ.

## 5. Реестр значимых атак и уязвимостей

| Атака / CVE | Цель | Суть | Статус |
|---|---|---|---|
| MS-CHAPv2 (Marlinspike/Ray, 2012) | PPTP | сводится к одному DES-ключу → 100 % взлом за ≤24 ч | не исправимо |
| Bit-flipping в MPPE | PPTP | нет контроля целостности | не исправимо |
| IKEv1 Aggressive Mode PSK | IPsec | хеш PSK до аутентификации → офлайн-брутфорс | отключить AM |
| Logjam (2015) | IPsec/TLS | downgrade до 512-bit DH; 1024-bit MODP по силам государству | DH ≥2048 / ECDH |
| Bleichenbacher в IKEv1 (2018) | IPsec | oracle в RSA-encrypted nonce → подмена | патчи вендоров |
| VORACLE (2018) | OpenVPN | сжатие до шифрования → утечка плейнтекста | `compress` выключить |
| DROWN / POODLE / BEAST | TLS-VPN | атаки на устаревшие версии TLS/SSL | TLS ≥1.2, лучше 1.3 |
| CVE-2018-13379 | Fortinet SSL-VPN | path traversal → выгрузка plaintext-паролей сессий | эксплуатируется до сих пор |
| CVE-2019-11510 | Pulse Secure | pre-auth чтение произвольных файлов | массово использовалась APT |
| CVE-2023-4966 «Citrix Bleed» | Citrix NetScaler | утечка токенов сессии → обход MFA | критично |
| CVE-2023-20269 | Cisco ASA/FTD | brute-force VPN-сессий без MFA | Akira/LockBit |
| CVE-2024-21887 + 2023-46805 | Ivanti | command injection + обход аутентификации | цепочка RCE |
| **TunnelCrack** (2023) | все VPN-клиенты | LocalNet/ServerIP-утечки: трафик уходит мимо туннеля | исправления в клиентах |
| **TunnelVision** CVE-2024-3661 | все VPN на базе маршрутов | DHCP option 121 переписывает таблицу маршрутов | нужна изоляция сетевого namespace |
| **Port Shadow** (2024) | OpenVPN/WireGuard/openconnect | shared-NAT на сервере → деанонимизация и перенаправление | конфигурация фаервола |
| CVE-2024-1086 и родственные | ядро + kernel-VPN | привилегированный код = высокая ставка | патч-менеджмент |
| Терминация в userspace (общее) | OpenVPN/SoftEther | больше парсеров = больше памяти-багов | привилегии, seccomp, chroot |

**Вывод из реестра:** за последние 5 лет ни одна массовая компрометация не произошла из-за
слома криптографии. Ломали **устройства терминации VPN** (Fortinet, Ivanti, Citrix, Cisco)
и **конфигурации** (утечки маршрутов, отсутствие MFA). Выбор протокола — примерно 20 % риска;
80 % — патч-менеджмент, MFA и сегментация за туннелем.

## 6. Производительность и накладные расходы

Ориентировочные значения. Стенд: два x86-64 узла с AES-NI, 10 GbE, MTU 1500, IPv4.

| Протокол | Overhead на пакет | Типичная пропускная способность | CPU на Гбит/с | Где исполняется |
|---|---|---|---|---|
| MACsec (ASIC) | 32 байта | line rate | ~0 | железо |
| IPsec ESP + AES-GCM (offload) | 54–73 байта | 9–10 Гбит/с | очень низкий | NIC/ядро |
| IPsec ESP + AES-NI | 54–73 байта | 3–6 Гбит/с | средний | ядро |
| WireGuard (kernel) | 60 байт | 2–8 Гбит/с (multi-queue) | низкий | ядро |
| WireGuard (wireguard-go) | 60 байт | 0,6–1,5 Гбит/с | высокий | userspace |
| OpenVPN DCO | ~70 байт | 1,5–4 Гбит/с | средний | ядро |
| OpenVPN UDP (классический) | ~70 байт | 200–600 Мбит/с | 🔴 высокий | userspace, 1 поток |
| OpenVPN TCP/443 | ~70 байт + TCP | 100–400 Мбит/с, деградация при потерях | высокий | userspace |
| OpenConnect/DTLS | ~60 байт | 1–2 Гбит/с | средний | userspace |
| SSTP | ~80 байт | 100–300 Мбит/с | высокий | userspace |
| L2TP/IPsec | ~100 байт (двойная инкапсуляция) | 0,5–2 Гбит/с | средний | ядро |
| GRE over IPsec | ~90 байт | 1–4 Гбит/с | средний | ядро |
| Hysteria 2 / QUIC | ~50 байт + QUIC | 0,5–2 Гбит/с | высокий | userspace |

**MTU — самая частая причина «VPN работает, но сайты не открываются».**
Практика: ставьте MTU туннеля 1420 (WireGuard IPv4), 1380 (IPv6/двойной NAT),
и обязательно разрешайте ICMP type 3 code 4 (Fragmentation Needed) — иначе PMTUD не работает
и вы получите чёрные дыры. Для TCP — `--mss-fix` / `TCPMSS --clamp-mss-to-pmtu`.

## 8. Пост-квантовая готовность

| Протокол | Механизм | Зрелость |
|---|---|---|
| IKEv2 | RFC 8784 (PPK — квантово-стойкий PSK) | 🟢 в strongSwan, Cisco, Juniper |
| IKEv2 | RFC 9370 (Multiple Key Exchanges → ML-KEM-768/1024 гибрид) | 🟢 strongSwan 6.x, libreswan |
| WireGuard | `PresharedKey` (256 бит) | 🟢 работает, но ключ статичен |
| WireGuard + Rosenpass | ML-KEM/Classic McEliece → ротируемый PSK | 🟡 молодой, но формально верифицирован |
| OpenVPN | через TLS 1.3 гибриды в OpenSSL 3.5 (X25519MLKEM768) | 🟡 появляется |
| TLS-VPN в целом | X25519MLKEM768 в браузерах/OpenSSL | 🟢 развёртывается массово |
| MASQUE/QUIC | наследует PQ-TLS 1.3 | 🟢 |
| PPTP/L2TP/IKEv1 | нет и не будет | ⚫ |

Если ваш трафик имеет ценность более 10 лет (гостайна, медицина, промышленные секреты,
персональные данные) — гибридный PQ-режим нужно включать **сейчас**, а не когда появится
криптографически релевантный квантовый компьютер. Перехват сегодня — расшифровка потом.

## 9. Что часто называют VPN, но это не VPN

| Технология | Что это на самом деле | Отличие |
|---|---|---|
| Tor | анонимизирующая overlay-сеть с луковой маршрутизацией | защищает от корреляции, а не от корпоративного периметра; медленный |
| HTTP/SOCKS-прокси | перенаправление на L4/L7 | нет шифрования по умолчанию, нет туннелирования IP |
| DNS over HTTPS/TLS | шифрование DNS-запросов | не туннелирует трафик, скрывает лишь имена |
| ZTNA / SDP (Zscaler, Cloudflare Access, Netskope) | доступ к приложению, а не к сети | правильная модель для BYOD: нет L3-доступа |
| SASE / SD-WAN | оркестрация + транспорт (внутри — IPsec) | архитектура, а не протокол |
| SSH jump host | контролируемый доступ к хостам | не сеть, а сессии |
| Смарт-DNS | подмена DNS-ответов | никакого шифрования |
| iCloud Private Relay | двухузловой QUIC-релей для Safari/трафика | не полный туннель, не даёт входящих соединений |

Различие важно организационно: покупая «VPN» для подрядчика, вы обычно покупаете ему
доступ ко всей плоской L3-сети. Это и есть типовой вектор развития атаки — почти каждый
крупный инцидент с шифровальщиками последних лет начинался с VPN-учётки без MFA.

## 10. Эксплуатационный чек-лист

**Протокол и криптография**
- [ ] PPTP, L2TP без IPsec, IKEv1, SSLv3/TLS 1.0/1.1 — отключены полностью.
- [ ] Только AEAD-шифры: AES-GCM или ChaCha20-Poly1305. `3DES`, `CBC+HMAC`, `RC4` — запрещены.
- [ ] PFS включён; DH-группа ≥ 2048-bit MODP, лучше ECP-384 / X25519.
- [ ] Rekey: IKE SA ≤ 4 ч, Child SA ≤ 1 ч.
- [ ] Гибридный PQ-обмен (RFC 9370 / PPK / WG PSK) — там, где данные долгоживущие.
- [ ] Компрессия в туннеле выключена (VORACLE, CRIME).

**Аутентификация**
- [ ] MFA обязательна для всего remote access. Без исключений для «сервисных» учёток.
- [ ] Клиентские сертификаты (mTLS / EAP-TLS) вместо или в дополнение к паролю.
- [ ] Проверка сертификата сервера на клиенте включена и не отключается пользователем.
- [ ] Процедура отзыва: CRL/OCSP для PKI, удаление публичного ключа для WireGuard.
- [ ] Учёт: кто, когда, с какого устройства — в SIEM.

**Сеть и утечки**
- [ ] Kill-switch / `AllowedIPs = 0.0.0.0/0, ::/0` при full-tunnel.
- [ ] Защита от TunnelVision: игнорирование DHCP option 121 или сетевой namespace.
- [ ] Защита от TunnelCrack: локальный трафик тоже в туннель (или явный allow-list).
- [ ] Утечки DNS и IPv6 закрыты (проверить обе стороны).
- [ ] MTU/MSS настроены, ICMP-3-4 не фильтруется.
- [ ] Split-tunnel — только по осознанному решению, с реестром исключений.

**Терминация и периметр**
- [ ] VPN-концентратор патчится в приоритетном порядке (см. реестр CVE выше).
- [ ] Управляющий интерфейс шлюза недоступен из интернета.
- [ ] Сегментация ЗА туннелем: VPN даёт доступ к сегменту, а не к плоской сети.
- [ ] Rate-limiting и cookie-механизмы против DoS на handshake.
- [ ] Для OpenVPN: `tls-crypt-v2`, запуск без root, seccomp/chroot.
- [ ] Мониторинг аномалий: вход из нового гео, невозможные перемещения, объёмы выгрузки.

## 11. Заключение

1. **Выбор протокола — решённая задача.** IKEv2/IPsec и WireGuard закрывают 95 % сценариев.
   OpenVPN/OpenConnect остаются как транспорт для враждебных сетей.
2. **Легаси нужно не «планировать к выводу», а выключать.** PPTP и IKEv1 Aggressive Mode —
   это не техдолг, а действующая уязвимость.
3. **Риск сместился с криптографии на реализации и периметр.** Инциденты 2019–2026 гг. —
   это Fortinet, Pulse, Citrix, Ivanti, Cisco и отсутствие MFA, а не слабые шифры.
4. **VPN — транспорт, а не модель доступа.** Для подрядчиков и BYOD архитектурно верный
   ответ — ZTNA с доступом к конкретным приложениям, а не L3-туннель в корпоративную сеть.
5. **Пост-квантовый переход начинается сейчас** для всего, что должно оставаться
   конфиденциальным дольше десятилетия.
